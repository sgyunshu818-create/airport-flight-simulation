# 机场航班仿真项目规划

## 1. 项目基本信息

项目名称：机场航班运行仿真系统  
英文名称：Airport Flight Simulation System  
项目类型：软件工程实验项目  
推荐技术路线：Java + VS Code + Maven + MySQL + Spring Boot + Thymeleaf  
核心目标：模拟机场中航班从计划、等待、滑行、起飞、降落、停机位分配到延误统计的全过程，并通过数据库和页面展示仿真运行结果。

本项目面向软件工程课程实验，重点不是追求工业级复杂度，而是完整体现软件工程开发流程，包括需求分析、概要设计、编码实现、测试验收和项目交付。项目应具有清晰的业务背景、明确的模块划分、合理的数据库设计、可运行的核心功能和可展示的测试结果。

## 2. 项目背景与选题说明

机场航班运行是一个典型的资源调度场景。机场中的跑道、停机位、滑行道、登机口等资源有限，而航班具有计划起飞时间、计划降落时间、机型、优先级等属性。当多个航班在相近时间内请求机场资源时，系统需要根据一定规则进行调度。如果资源不足，航班就会进入等待状态并产生延误。

本项目通过建立一个简化的机场运行模型，对航班运行过程进行仿真。系统可以录入航班计划和机场资源信息，按照时间步推进仿真过程，自动分配跑道和停机位，并记录航班状态变化、延误时间和资源利用情况。

选择该项目的原因：

1. 业务场景清晰，容易进行需求分析和建模。
2. 涉及数据库设计，适合体现实体关系和数据持久化。
3. 包含调度算法，具有一定技术含量。
4. 可以通过页面、表格和统计结果进行展示。
5. 适合产出需求文档、概要设计文档、测试报告和演示 PPT。

## 3. 项目建设目标

### 3.1 总体目标

开发一个基于 Java 的机场航班仿真系统，实现航班计划管理、机场资源管理、航班运行仿真、资源调度、延误统计和仿真结果展示等功能。

系统应能够：

1. 管理航班基本信息和计划时间。
2. 管理机场跑道、停机位等核心资源。
3. 根据仿真时间推进航班状态。
4. 根据调度规则分配跑道和停机位。
5. 在资源不足时产生等待队列和延误记录。
6. 统计航班完成情况、延误情况和资源利用情况。
7. 通过页面或接口展示仿真过程和结果。

### 3.2 课程实验目标

本项目需要体现软件工程实验的完整过程：

1. 需求分析：明确用户角色、功能需求、非功能需求和业务流程。
2. 概要设计：完成系统架构设计、模块设计、数据库设计和核心算法设计。
3. 编码实现：完成可运行的软件系统。
4. 测试验收：设计测试用例，执行功能测试、异常测试和核心算法测试。
5. 文档交付：提交源码、数据库脚本、需求分析说明书、概要设计说明书、测试报告和演示材料。

## 10. 航班仿真运行模块

### 10.1 模块目标

根据仿真任务设置，按照时间步推进航班运行过程，触发航班状态变化和资源调度。

### 10.2 主要功能

1. 创建仿真任务。
2. 设置仿真开始时间。
3. 设置仿真结束时间。
4. 设置时间步长，例如 5 分钟或 10 分钟。
5. 启动仿真。
6. 单步推进仿真。
7. 自动运行完整仿真。
8. 重置仿真。
9. 记录每一步仿真事件。

### 10.3 仿真时间推进方式

建议采用离散时间步仿真。

示例：

```text
仿真开始时间：2026-06-01 08:00
仿真结束时间：2026-06-01 12:00
时间步长：5 分钟
```

系统每次推进 5 分钟，检查当前时间点是否有航班需要进入等待队列，并尝试为航班分配跑道和停机位。

### 10.4 起飞航班状态流转

起飞航班可以采用如下流程：

```text
计划中 -> 等待中 -> 等待跑道 -> 起飞中 -> 已起飞/完成
```

更详细版本：

```text
计划中 -> 等待登机口 -> 滑行中 -> 等待跑道 -> 起飞中 -> 已起飞 -> 完成
```

课程项目中推荐先使用简化版本。

### 10.5 降落航班状态流转

降落航班可以采用如下流程：

```text
计划中 -> 等待降落 -> 占用跑道 -> 滑行至停机位 -> 已到达 -> 完成
```

简化版本：

```text
计划中 -> 等待中 -> 降落中 -> 已到达 -> 完成
```

### 10.6 仿真事件记录

每次状态变化都应该记录为仿真事件。

事件示例：

```text
08:00 航班 MU5101 进入等待队列
08:05 航班 MU5101 分配到跑道 R01
08:10 航班 MU5101 起飞完成
08:15 航班 CA1202 因无空闲跑道继续等待，延误 5 分钟
```

这些记录可以用于页面展示，也可以用于测试报告截图。

## 11. 调度算法模块

### 11.1 模块目标

根据航班计划时间、航班类型、优先级和资源状态，为等待队列中的航班分配跑道和停机位。

### 11.2 基础调度算法

推荐基础版本使用先到先服务算法：

```text
FCFS：First Come First Served
```

基本规则：

1. 计划时间越早，优先级越高。
2. 同一时间进入等待队列的航班，降落航班优先于起飞航班。
3. 跑道空闲时，从等待队列中选择优先级最高的航班。
4. 如果没有空闲跑道，航班继续等待。
5. 如果降落航班没有可用停机位，航班继续等待。
6. 等待时间累加为延误时间。

### 11.3 推荐优先级规则

可以设计一个综合优先级：

```text
优先级分数 = 航班基础优先级 + 延误时间权重 + 航班类型权重
```

示例：

1. 降落航班权重高于起飞航班。
2. 延误时间越长，优先级越高。
3. 紧急航班优先级最高。
4. 计划时间更早的航班优先。

基础版本可以先不实现复杂权重，只在报告中说明可扩展方向。

### 11.4 调度伪代码

```text
每次仿真时间推进时：
    1. 查找计划时间小于等于当前时间且未完成的航班
    2. 将符合条件的航班加入等待队列
    3. 查询当前空闲跑道
    4. 查询当前空闲停机位
    5. 按调度规则排序等待队列
    6. 依次处理等待航班
        如果是起飞航班：
            如果存在可用跑道：
                分配跑道
                更新航班状态
                记录仿真事件
            否则：
                增加延误时间
        如果是降落航班：
            如果存在可用跑道且存在可用停机位：
                分配跑道和停机位
                更新航班状态
                记录仿真事件
            否则：
                增加延误时间
    7. 释放已经完成占用时间的跑道
    8. 更新统计数据
```

## 14. 系统架构设计

### 14.1 推荐架构

采用经典三层架构：

```text
表现层 Controller / Thymeleaf 页面
        ↓
业务层 Service
        ↓
数据访问层 Repository / Mapper
        ↓
MySQL 数据库
```

### 14.2 分层职责

表现层：

1. 接收用户请求。
2. 调用业务层方法。
3. 返回页面或 JSON 数据。
4. 展示航班、资源和统计结果。

业务层：

1. 实现航班管理业务。
2. 实现机场资源管理业务。
3. 实现仿真时间推进。
4. 实现调度算法。
5. 计算延误和统计数据。

数据访问层：

1. 查询航班数据。
2. 查询跑道数据。
3. 查询停机位数据。
4. 保存仿真任务。
5. 保存仿真记录。

数据库层：

1. 持久化航班信息。
2. 持久化机场资源。
3. 持久化仿真任务和仿真日志。

## 17. 核心业务流程

### 17.1 总体流程

```text
1. 管理员录入机场资源
2. 管理员录入航班计划
3. 创建仿真任务
4. 系统按时间步推进仿真
5. 每个时间点检查待起飞或待降落航班
6. 调度算法分配跑道和停机位
7. 更新航班状态和资源状态
8. 写入仿真事件记录
9. 仿真结束后生成统计结果
```

### 17.2 航班进入等待队列流程

```text
1. 获取当前仿真时间
2. 查询计划时间小于等于当前时间的航班
3. 判断航班是否已经完成或取消
4. 如果未完成，则加入等待队列
5. 记录进入等待队列事件
```

### 17.3 起飞调度流程

```text
1. 获取等待起飞航班
2. 按计划起飞时间排序
3. 检查是否存在可用跑道
4. 如果有跑道：
    分配跑道
    更新航班状态为起飞中
    设置实际起飞时间
    记录仿真事件
5. 如果无跑道：
    航班继续等待
    增加延误时间
```

### 17.4 降落调度流程

```text
1. 获取等待降落航班
2. 按计划降落时间排序
3. 检查是否存在可用跑道
4. 检查是否存在适合机型的空闲停机位
5. 如果跑道和停机位都可用：
    分配跑道和停机位
    更新航班状态为降落中
    设置实际降落时间
    记录仿真事件
6. 如果资源不足：
    航班继续等待
    增加延误时间
```

## 26. 风险与控制

### 26.1 风险一：功能范围过大

控制方式：

1. 优先完成基础版功能。
2. 天气、图表、登录等功能放到增强版。
3. 先保证系统能完整运行，再考虑美化。

控制方式：

1. 先实现 FCFS 先到先服务。
2. 后续再加入优先级。
3. 报告中说明算法扩展思路即可。

### 26.3 风险三：页面开发耗时

控制方式：

1. 使用 Thymeleaf 表格页面。
2. 不做复杂前端框架。
3. 先实现可用页面，再进行简单美化。

### 26.4 风险四：数据库表设计反复修改

控制方式：

1. 先确定核心表：flight、runway、gate、simulation_task、simulation_record。
2. 字段不要过度复杂。
3. 后续新增字段时同步更新 SQL 脚本和文档。
